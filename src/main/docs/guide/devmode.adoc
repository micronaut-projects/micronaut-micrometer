In development mode, when the application restarts after a change, each generation of the application creates its own `MeterRegistry`, with its own registries, filters and binders, and the registry of the stopped generation is closed with it. The meters therefore start again from zero after each restart, as they do when the process restarts: the Prometheus `rate()` and `increase()` functions, for example, treat a counter that goes back to zero as a reset.

The registry is not kept across restarts because a registry cannot let go of what the application gave it. Micrometer offers no way to remove a `MeterFilter` from a registry, so the filters of every generation would pile up, and those of the application would keep running its old code. The meters of a registry also hold the functions they are computed by, such as the lambda of a gauge, which are often classes of the application: a registry that outlived its generation would keep that generation's classes, and with them its class loader, alive.

The JVM binder (`micronaut.metrics.binders.jvm`) and the Logback binder (`micronaut.metrics.binders.logback`) register with objects that outlive the application: the JVM binder adds a notification listener to the garbage collector beans of the JVM, and the Logback binder a turbo filter to the Logback context. Both are closed with the context that created them, which removes the listener and the filter, so that they keep neither the registry of a stopped generation nor record into it. This also applies outside development mode, whenever an application context is closed.
