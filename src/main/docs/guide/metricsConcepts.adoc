== Metric Concepts

Key Micrometer https://micrometer.io/docs/concepts[concepts] include a https://micrometer.io/docs/concepts#_registry[MeterRegistry] to register and use meters.
A https://micrometer.io/docs/concepts#_meters[Meter] is something that produces metrics.

A MeterRegistry can have some customizations automatically applied.

=== Meter Registry Configurer

* Any bean that implements `MeterRegistryConfigurer` gets applied to every _applicable_ MeterRegistry bean on creation
* The implementation of the MeterRegistryConfigurer `supports()` method determines if the configurer is applied to a particular registry
** If you want all registries to get the customization, return `true`
** Otherwise, you can evaluate the registry for its class type, class hierarchy, or other criteria.
** Remember you only get one shot for autoconfiguration; i.e. when the bean context is started.
** However, in code you can apply additional customizations to the registry config.

Micronaut can also add common tags to every meter via configuration. The legacy `micronaut.metrics.tags.*` prefix remains supported, and `micronaut.metrics.common-tags.*` is available as a clearer alias.
When both prefixes configure the same tag key, `micronaut.metrics.common-tags.*` takes precedence.

[configuration]
----
micronaut:
  metrics:
    common-tags:
      application: ${micronaut.application.name}
      region: us-east-1
----

* A https://micrometer.io/docs/concepts#_meter_filters[meter filter] can be used to determine if a Meter is to be added to the registry.

==== Configuring Meters with Properties

Common filters can be declared in configuration instead of code. Every key below ends with a meter name prefix: a key applies to meters whose name equals the prefix or starts with the prefix followed by a dot. When several prefixes match, the most specific (longest) one wins. Where noted, the special key `all` applies to every meter that no other key matches.

[configuration]
----
micronaut:
  metrics:
    enable:
      jvm.gc: false
      http.client: false
    distribution:
      percentiles-histogram:
        http.server.requests: true
      percentiles:
        all: 0.5,0.95,0.99
      slo:
        http.server.requests: 100ms,500ms,1s
      minimum-expected-value:
        http.server.requests: 5ms
      maximum-expected-value:
        http.server.requests: 10s
----

.Meter filter properties
|=======
|*Property* |*Type* |*`all` key* |*Description*
|`micronaut.metrics.enable.<prefix>` |boolean |yes |Set to `false` to deny meters whose names start with the prefix.
|`micronaut.metrics.distribution.percentiles-histogram.<prefix>` |boolean |yes |Whether to publish a histogram suitable for computing aggregable percentile approximations.
|`micronaut.metrics.distribution.percentiles.<prefix>` |list of doubles |yes |Client-side computed percentiles to publish, for example `0.5,0.95,0.99`. They cannot be aggregated across dimensions.
|`micronaut.metrics.distribution.slo.<prefix>` |list of values |no |Service level objective boundaries.
|`micronaut.metrics.distribution.minimum-expected-value.<prefix>` |value |no |The minimum value the meter is expected to observe. It bounds the histogram buckets that are published.
|`micronaut.metrics.distribution.maximum-expected-value.<prefix>` |value |no |The maximum value the meter is expected to observe. It bounds the histogram buckets that are published.
|`micronaut.metrics.distribution.expiry.<prefix>` |duration |yes |How long samples are accumulated in decaying distribution statistics before they are reset and rotated.
|`micronaut.metrics.distribution.buffer-length.<prefix>` |integer |yes |The number of histograms to keep in the ring buffer.
|=======

Values for timers are durations such as `100ms` or `PT1S`; a plain number is read as milliseconds. Values for distribution summaries are plain numbers. Because the unit depends on the meter type, `slo`, `minimum-expected-value` and `maximum-expected-value` do not support the `all` key.

The filter only exists when at least one of these properties is set. Like any `MeterFilter`, it is consulted when a meter is first registered and not when values are recorded. It is applied after the other filters, so its distribution settings take precedence over the `micronaut.metrics.binders.web.server` and `micronaut.metrics.binders.web.client` settings, which remain available as shortcuts for the `http.server.requests` and `http.client.requests` meters.

=== Meter Binder

Meter Binders get applied to Meter Registry to _mix in_ metrics producers. Micrometer defines several of these for cross-cutting metrics related to JVM metrics, caches, classloaders, etc. These implement `MeterBinder`, but they are not autowired as beans; manual wiring is required given how Micrometer is currently implemented.

===== Web Metrics

There is a default web filter provided for web metrics. All routes, status codes, methods, and exceptions are timed and counted.

*Control Property*: `micronaut.metrics.binders.web.enabled`

NOTE: CORS preflight requests that are handled before application route matching are not recorded as normal server request metrics.
This avoids creating `http.server.requests` metrics with high-cardinality URI tags when no route template is available for the `OPTIONS` request.

.When requests are recorded
Each request is recorded exactly once.

* A server request is timed from the moment it enters the filter chain until its response has been completely written, including a streamed body (for example a `Publisher` or `Flux` returned by a controller). If the client disconnects while the body is streamed, the request is recorded when the connection closes, with the status of the response. If writing the body fails before anything was sent, the request is recorded with the error response that replaced it. WebSocket upgrade requests are recorded when the response filters run.
* A client request is recorded when its response or failure is received, or when the request is cancelled before that. A cancelled request is recorded with the status `CLIENT_ERROR` and the exception `CancellationException`.

NOTE: Because the server timer is recorded once the response has been written, it can be recorded slightly after the client received the response. Tests that check `http.server.requests` right after a call returns should poll, for example with `PollingConditions` or Awaitility.

.Filter Path
If enabled, by default the path `/**` is intercepted. To change which paths are run through the filter for the server, set `micronaut.metrics.http.path`. For the client, set `micronaut.metrics.http.client.path`.

.Excluding paths
To avoid recording some requests, for example health checks or scrapes of the Prometheus endpoint, list regular expressions of the paths to exclude. A request is not recorded when its path matches one of the expressions entirely. Set `micronaut.metrics.http.exclusions` for the server and `micronaut.metrics.http.client.exclusions` for the client:

[configuration]
----
micronaut:
  metrics:
    http:
      exclusions:
        - /health.*
        - /prometheus
      client:
        exclusions:
          - /internal/.*
----

Alternatively, a `MeterFilter` bean can deny the meters of some URIs, for example `MeterFilter.deny(id -> id.getName().startsWith("http.server.requests") && "/health".equals(id.getTag("uri")))`.

.Client service ID tag
The `http.client.requests` timers always have the `serviceId` tag, so that all the client timers have the same tag keys, which some registries such as Prometheus require. It is the ID of the service of a declarative client (`embedded-server` for a client of the application's own server), and `none` for a client without a service ID, for example one created with `HttpClient.create(url)`.

.Client error URI reporting

By default, client URIs are captured when an error is handled.
This can cause trouble in some monitoring tools due to a large amount of distinct URIs captured.
This URI capturing can be disabled by setting `micronaut.metrics.binders.web.client-errors-uris.enabled` to `false`.

.Custom tags

To add request-aware custom tags to the built-in HTTP server and client metrics, create a bean that implements `HttpMetricsTagProvider`.
Each provider is invoked once per request, when Micronaut records `http.server.requests` or `http.client.requests`: with the final response of a server request, and with the response or the failure of a client request (the response is `null` when the client request failed without one or was cancelled).
A tag of a provider replaces a default tag with the same key.
Without provider beans, the web metrics do no extra work.

NOTE: The tags must have a low cardinality: every distinct combination of tag values creates a new timer.

.Customizing

The web metrics can be configured to enable percentiles, histogram, service level objectives and the expected min and max duration of the requests.
All configurations can be added to HTTP server and client metrics. All time configurations are specified in seconds.

A complete example:

[configuration]
----
micronaut:
  metrics:
    binders:
      web:
        server:
          percentiles: "0.95,0.99"
          histogram: true
          slos: "0.1,0.4,0.5,2"
          min: 0.1
          max: 60
        client:
          percentiles: "0.95,0.99"
          histogram: true
          slos: "0.1,0.4,0.5,2"
          min: 0.1
          max: 60
----

.Metrics provided
|=======
|*Name*
| http.server.requests
| http.client.requests
|=======

.Limiting URI tags

The `uri` tag of the HTTP meters uses the route template (for example `/books/{id}`), so its number of values is normally bounded by the number of routes.
If requests are not matched to templates, for example when a client calls absolute URLs without a template, every distinct URI creates a new time series.
To protect the meter registry and the monitoring backend, you can cap the number of distinct `uri` values. Once the limit is reached, meters with new `uri` values are not registered and a warning is logged once.

[configuration]
----
micronaut:
  metrics:
    binders:
      web:
        server:
          max-uri-tags: 100
        client:
          max-uri-tags: 100
----

.URI tag limit properties
|=======
|*Property* |*Type* |*Default* |*Description*
|`micronaut.metrics.binders.web.server.max-uri-tags` |integer |not set (disabled) |The maximum number of distinct `uri` tag values of the `http.server.requests` meters. Zero or a negative value disables the limit.
|`micronaut.metrics.binders.web.client.max-uri-tags` |integer |not set (disabled) |The maximum number of distinct `uri` tag values of the `http.client.requests` meters. Zero or a negative value disables the limit.
|=======

The limits match meters by name, so they also apply to the meters of the <<observation, Micrometer Observation HTTP>> module, including the `http.server.requests.active` long task timers. They are implemented as meter filters, so they are only consulted when a meter is first registered.

===== Startup Time Metrics

The startup time metrics report how long the application took to start, measured as the JVM uptime when the event is published, so they include the time spent before the application context was created.

* `application.started.time` is registered when the application context has started.
* `application.ready.time` is registered when an embedded application, such as the HTTP server, has started. If the application has no embedded application, it has the same value as `application.started.time`.

Both gauges have a `main.application.class` tag when the JVM reports the main class. The tag is omitted when the application was started with `java -jar` or in a native image.

*Control Property*: `micronaut.metrics.binders.startup.enabled` (default `true`)

===== Netty Metrics

Currently, the following binders are provided to instrument Netty event loops and server channels:

* *Executor binder*: When `micronaut.metrics.binders.executor.enabled` is enabled, configured Netty event loop groups also expose `executor.queued` and `executor.pool.size` metrics tagged with the event loop group name.
* *Netty queue binder*: Instrument and expose Netty event loop queue metrics for event loop groups used by the server and HTTP clients; use `micronaut.metrics.binders.netty.queues.enabled` to toggle. Default is *false*. The queues' size and tasks wait and execution time are exposed, tagged with the `group` of the event loop: `worker` for the server's worker group, `parent` for its acceptor group, and the configured name for other groups, such as the `micronaut.netty.event-loops.*` group an HTTP client selects with `micronaut.http.services.*.event-loop-group`.
+
NOTE: The queues are instrumented for the event loop groups configured with `micronaut.netty.event-loops.*`, and for the server's worker group. The server creates its own acceptor group when `micronaut.netty.event-loops.parent` is not configured, and that group is not instrumented. Configure it, for example with `micronaut.netty.event-loops.parent.num-threads: 1`, to get the `parent` queue metrics.
* *ByteBufAllocatorMetricsBinder*: Expose `ByteBuf` default allocators (https://netty.io/4.2/api/io/netty/buffer/ByteBufAllocatorMetric.html[UnpooledByteBufAllocator], https://netty.io/4.2/api/io/netty/buffer/PooledByteBufAllocatorMetric.html[PooledByteBufAllocator], https://netty.io/4.2/api/io/netty/buffer/AdaptiveByteBufAllocator.html[AdaptiveByteBufAllocator]) metrics; use `micronaut.metrics.binders.netty.bytebuf-allocators.enabled` to toggle. Default is *false*.
The server and the HTTP clients use Netty's default allocator, which the `io.netty.allocator.type` system property selects. Since Netty 4.2 the default allocator is the adaptive allocator (`alloc=adaptive`); the pooled allocator (`alloc=pooled`) is only metered when it is the default allocator (`-Dio.netty.allocator.type=pooled`).
You can customize what metrics are exposed using `micronaut.metrics.binders.netty.bytebuf-allocators.metrics`. By default, all available metrics are exposed. These flags are supported:
** `ADAPTIVE_ALLOCATOR`: expose `AdaptiveByteBufAllocator` metrics, when it is the default allocator,
** `POOLED_ALLOCATOR`: expose `PooledByteBufAllocator` metrics, when it is the default allocator,
** `UNPOOLED_ALLOCATOR`: expose `UnpooledByteBufAllocator` metrics,
** `POOLED_ARENAS`: expose `PooledByteBufAllocator` pooled arenas metrics (requires `POOLED_ALLOCATOR`),
** `POOLED_ARENAS_SUBPAGES`: expose `PooledByteBufAllocator` pooled arenas sub pages metrics (requires `POOLED_ARENAS`),
** `POOLED_ARENAS_CHUNKLISTS`: expose `PooledByteBufAllocator` pooled arenas chunk lists metrics (requires `POOLED_ARENAS`),
** `POOLED_ARENAS_CHUNKS`: expose `PooledByteBufAllocator` pooled arenas chunks metrics (requires `POOLED_ARENAS_CHUNKLISTS`).
* *NettyMetricsPipelineBinder*: Instrument Netty's connection channels (HTTP/1.1, h2c and HTTP/2 over TLS; for HTTP/3 the UDP channel of the listener), use `micronaut.metrics.binders.netty.channels.enabled` to toggle. Default is *false*.
The provided metrics include the channel count, current active channel count, channel error count, bytes read and written.

===== HTTP Client Pool Metrics

The connection pools of the Netty HTTP clients can be instrumented with `micronaut.metrics.binders.web.client.pool.enabled=true`. Default is *false*. The meters cover the connections and requests of every HTTP client in the application, declarative clients included, and every per-host pool of those clients. They have no client or host tag, so the per-host pools that a client creates and evicts never leave meters behind. WebSocket connections are not pool connections and are not counted.

.HTTP Client Pool Metrics provided
|=======
|*Name* |*Type* |*Tags* |*Description*
| http.client.pool.connections | Gauge | `state=open` | Connections that the pools can use
| http.client.pool.connections | Gauge | `state=pending` | Connection attempts in progress, until the TLS handshake and the protocol negotiation are done
| http.client.pool.connections.created | Counter | `protocol` (`http/1.1`, `h2`, `h3`) | Connections established
| http.client.pool.connections.create.time | Timer | `protocol` (`http/1.1`, `h2`, `h3`) | Time from the start of a connection attempt until the connection is established
| http.client.pool.connections.failed | Counter | | Connection attempts that closed before the connection was established
| http.client.pool.requests | Gauge | `state=active` | Requests running on a pool connection
|=======
